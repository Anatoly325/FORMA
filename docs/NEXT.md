# Следующие проверяемые этапы

Первая поставка подтверждает исполнимость языка и рабочего цикла. Она не
устанавливает мировую новизну, универсальное преимущество или предпочтение моделей.

## 1. Усилить ядро и практическую библиотеку

Добавить закрытые варианты `Option`/`Result`, исчерпывающий `match` и явные
ошибки пользовательских инструментов. Затем — модули с фиксированными версиями,
индексируемые словари/группировку для линейной сверки, даты и временные зоны,
экспорт CSV и потоковую обработку. Для каждого расширения сначала определить
типовые правила, ошибки и границы ресурсов.

Сохранить малое ядро: HTTP, файлы, GPU и вызовы моделей подключать через явные
стандартные профили возможностей. Не добавлять их как скрытые эффекты чистых функций.

## 2. Проверить экономику на реальных агентах

Подготовить отложенный набор задач с независимыми критериями приёмки:
преобразование данных, создание API-обёрток после появления HTTP, исправление
существующего инструмента, повторное использование и изменение требования.
Не использовать демонстрационные случаи как единственный экзамен.

Сравнить FORMA и Python на одинаковых моделях, задачах, правах, бюджетах и
доступе к справке. У Python должны быть обычные доступные библиотеки и нормальные
средства проверки; искусственно слабая контрольная группа ничего не доказывает.
Учитывать цену ознакомления модели с новым языком и все повторные попытки.

Показатели: доля подтверждённых успехов, полная стоимость всех запусков на
подтверждённый успех, время, количество исправлений, объём переданного контекста,
повторное использование. При нуле успехов стоимость успеха не считается конечной.
Опубликовать результаты по задачам и моделям, а не один удобный средний процент.

Начать с фиксированной модели и одного агента. Отдельно проверить JSON-диагностику,
выборочный контекст и правки по функциям, чтобы различать вклад механизмов.
Счётчик `fuelUsed` текущего прототипа не заменяет токеновую статистику провайдера.

## 3. Подключить агентную среду

После проверенного одиночного цикла реализовать координатор и двух исполнителей:
изолированные кандидаты, проверяемые выходы задач, общий бюджет, отмена,
повторная доставка результатов и проверка интеграции. Механический стенд не должен
выдаваться за исследование эффективности реальных LLM.

Следом — стандартный профиль `AgentSpec` и структурированное создание потомков
из FORMA. Создаётся контекст и цикл исполнения агента, а не новые веса модели.
Внешние действия требуют явных возможностей; отмена задачи не откатывает мир.

Выбор моделей остаётся экспериментальной политикой среды. Сравнить фиксированную
модель, начальный выбор и эскалацию с учётом переноса контекста, потери кеша,
стоимости маршрутизатора и повторной работы. Параллелизм оценивать отдельно по
скорости и по полной стоимости всех ветвей.

## 4. Переносимость

Сначала воспроизвести текущий профиль на Windows и macOS с закреплённой Node.js.
Затем реализовать backend Wasm и проверить одинаковую семантику на общем наборе
программ. Доступ к API платформы определяется её импортами и профилем среды;
сам Wasm не создаёт универсальных сетевых, файловых или GPU-возможностей.

На каждом этапе сохранять явно различимые статусы: задумано, реализовано,
проверено на указанных сценариях, измерено на реальных агентах.
